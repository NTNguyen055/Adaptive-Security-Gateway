## 1. Responsibilities and trust boundary

- Observations enter through `security_shadow.log()` and the server-owned `security_signal_adapter` trace, with detector invocation and result attributed to the `waf_sqli_xss` module.
- Only `waf_sqli` and `waf_xss` are eligible. A risk score, JWT rejection, rate limit, brute-force counter, untrusted header or WAF label claimed by a different detector **cannot** become confirmed-exploit evidence.
- `ngx.var.remote_addr` supplies the direct TCP peer identity; `ngx.var.request_id` is used for per-request deduplication. No client-supplied `X-Real-IP` / XFF is accepted as authority in this integration.
- Observation state is ephemeral, inside `ngx.shared.security_correlator_cache` (5 MB) with bounded per-key TTL (up to 360 seconds); five 60-second buckets form the correlation lookback. Restart/eviction can lose counters; this is not durable audit storage.
- A request containing both SQLi and XSS is counted **once**, with one class assigned by current source logic (SQLi takes precedence). Eight or more WAF-observed requests across at least three distinct buckets and two classes can produce `SUSPICIOUS_SHADOW`.
- `SUSPICIOUS_SHADOW` is a **suspicion/telemetry classification**, not confirmed exploitation or independently verified detector corroboration; by design it never invokes automatic ban issuance.
- `security_correlator.verify()` always returns `nil, "independent_evidence_and_nat_assessment_unavailable"`. This is an explicit authorization boundary, not a runtime error that should be suppressed or bypassed.

## 2. Why `verify()` stays closed

The separate `ip_ban_authorizer.lua` policy requires all of the following before any new automatic temporary IP ban:

1. Server-verified *confirmed* exploit events, not raw WAF matches or accumulated Risk Score.
2. Independently verified corroborating sources, not SQLi and XSS labels generated by one WAF.
3. At least eight verified exploit events, three distinct windows, two attack classes, and a verified event span of at least 120 seconds.
4. A verified low-collateral NAT assessment (`nat_assessment = "low_collateral_verified"`, `shared_ip_observed = false`) for a canonical trusted peer IP.
5. A trusted in-process issuer and reauthorization at the Redis writer boundary; the policy TTL cap is 300 seconds.

The current correlator does **not** possess a trustworthy independent exploit verifier or NAT assessment producer. A shared/unknown NAT address must not be treated as safe merely because no shared use was observed. Consequently the `ip_ban_issuer.lua` production path cannot issue a ban from this correlator.

**Important separation:** `nginx/tests/test_authorized_ban_live.sh` extracts the exact Redis `ISSUE_SCRIPT` and invokes it directly with synthetic test data. Its 10/10 PASS proves Redis atomic state, TTL/provenance, enforcement and expiry; it **does not** prove that the production correlator issued a ban. Manual SET `blacklist_ips` and Legacy key `blacklist:<ip>` remain distinct from `ban:v2:ip:<ip>`.

### 3.2. `nginx/lua/security_shadow.lua` — accepted WAF observation

The hook is called from `log_by_lua_block`, after `adapter.finish()`, **before** the policy report suppression/early return. The following is the authoritative parameter/guard logic in `4e7b350`:

```lua
if (os.getenv("SECURITY_CORRELATOR_SHADOW_ENABLED") or "false"):lower() == "true" then
    local call_ok, summary, correlation_err = pcall(
        correlator.observe,
        {
            trace = state.trace,
            peer_ip = ngx.var.remote_addr,
            request_id = ngx.var.request_id,
            -- An earlier WAF block may intentionally skip downstream JWT.
            -- Correlator still requires a completed, attributed WAF step.
            partial = state.instrumentation_error ~= nil
                or state.trace.required_control_failed == true
                or #report.errors > 0
                or state.trace.seen.waf_sqli_xss ~= true,
        }
    )

    if not call_ok then
        log_error("correlator_crashed")
    elseif not summary then
        log_error("correlator_error: " .. tostring(correlation_err))
    elseif summary.notify then
        ngx.log(
            ngx.WARN,
            "[SECURITY_CORRELATOR] status=SUSPICIOUS_SHADOW",
            " events=", summary.event_count,
            " windows=", summary.distinct_windows,
            " classes=", summary.distinct_attack_classes,
            " automatic_ban=disabled"
        )
    end
end
```

The critical correction is **not** using `skipped_required` in the correlator-specific `partial` expression. With early WAF denial, downstream JWT can legitimately be skipped. This does **not** change `partial` in the separate Security Policy Shadow report and does **not** bypass WAF, JWT, manual bans or other live controls.

## 5. Known limitations and operational guardrails

- **Shadow-only by design:** This correlator is not a verified independent exploit detector or NAT assessment engine. Runtime auto-issuance is **not** enabled.
- **Shared IP / CGNAT:** Per-peer counters can aggregate unrelated users. IP-specific automatic blocking requires a separate low-collateral proof, otherwise deny issuance.
- **Ephemeral state:** `ngx.shared` counters are bounded and volatile; collisions/eviction/restart can reduce observed counts; no durable, immutable audit store is provided.
- **Approximate identity key:** `ngx.md5(peer_ip)` is used to shorten *internal cache keys*, never as a cryptographic authentication primitive.
- **Observability semantics:** `security_shadow.log()` emits the Correlator warning **only when `summary.notify=true`**. Before threshold, `OBSERVED` events may not appear in WARN logs; an empty `grep` is not evidence the module failed.
- **Short-circuit policy diff:** Earlier Shadow Policy comparison logged `403` live versus `503` policy when WAF blocked before JWT. This is a comparison/attribution edge case for future regression, not a Gateway HTTP 503 observation.
- **Logging privacy:** Correlator's own status line omits raw IP/payload/account; however OpenResty error/WAF lines in the same Docker stream can include query/payload and peer IP. Apply redaction, retention and access control (P0.6); do not publish raw production logs.
- **Generalization:** A controlled eight-request local test does not establish FPR, performance, attack efficacy or production reliability. Those require labeled experiments and benchmarks (P0.6–P0.8, P5).
- **Feature flags:** The accepted local state leaves `SECURITY_CORRELATOR_SHADOW_ENABLED=false`; `SECURITY_SHADOW_ENABLED=true` may remain for the broader policy shadow. Keep V3 login accounting OFF unless explicitly rolled out with tests.
